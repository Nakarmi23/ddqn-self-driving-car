# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A self-driving car simulation trained with a Double Deep Q-Network (DDQN). A pygame car drives a fixed race track, casting rays to sense walls, and a PyTorch agent learns to steer/accelerate through checkpoints via reinforcement learning. There is no manual-play mode — `main.py` starts training, which runs until `agent.step_count` reaches `Game.TOTAL_TRAIN_STEPS` (1M learning steps), a greedy evaluation meets the early-stop bar, or the window is closed (or Ctrl+C in headless mode); every exit saves `checkpoint_latest.pt` the same way.

## Running

```bash
# Windows venv is already set up in .venv/
.venv\Scripts\activate
python main.py
# HEADLESS=1 (no window, no frame cap) or RENDER_EVERY=N (draw every Nth step, no cap) for fast training
```

There is no lint/build config. Tests are stdlib `unittest` (no pytest) under `tests/`: `python -m unittest discover -s tests -t .`. The other check is `python -m scripts.check_spawns`, which exits 1 if any track template has a bad spawn (see `game/game_spawn.py`). Training progress prints to stdout per step/episode, including a `[DDQNAgent] Using device: ...` line at startup showing whether it's running on CUDA, MPS, or CPU — see README for installing a GPU-enabled `torch` build per platform.

## Architecture

**Training loop lives in `game/__init__.py` (`Game` class), not `main.py`.** `main.py` just does `Game().run()`. `Game.run()` is an outer loop over episodes until the step budget is spent, with an inner loop (`_run_episode`) that steps the environment until collision, `MAX_STEPS_PER_EPISODE`, `STALL_LIMIT` (1000) steps without a checkpoint, or the budget running out mid-episode. Crash and stall timeout are failures (crash penalty, stored `done=True`); hitting `MAX_STEPS_PER_EPISODE` or the budget is truncation (no penalty, `done=False`). After every `EVAL_EVERY` (50)-th episode, once warm-up is over, `Game.evaluate()` runs `EVAL_EPISODES` (1 — spawn, physics and argmax are deterministic, so more would replay it) greedy episode(s) through the same `_run_episode(training=False)` (argmax via `choose_action(state, greedy=True)`, no `store_experience`/`learn`, epsilon untouched, same render/frame-cap settings) and scores them with `game/game_eval.py` (`summarize`, `laps_completed` — the first cp0 pass is the start line, so a lap is `num_checkpoints` passes after it; `is_better` ranks by mean then min checkpoints passed, never shaped reward). One more round runs when the budget is spent, so the final policy is scored too (the episode the budget cuts short is not logged; a resumed run whose budget is already spent exits without training or evaluating). Training stops early when every episode of a round completes `EARLY_STOP_LAPS` (2) laps (`game_eval.meets_lap_target`); set it to `None` to disable. Look here first for anything about reward shaping, episode/epsilon bookkeeping, or save/load.

**Agent lives in `ai/ddqn_agent.py` (`DDQNAgent`, built on PyTorch).** Owns the online/target `QNetwork` (`nn.Module`) networks, epsilon-greedy action selection, the prioritized replay buffer (`ai/replay_buffer.py`, `PrioritizedReplayBuffer`: numpy ring buffers + sum-tree/max-tree, capacity `MEMORY_CAPACITY` = 100k, O(log n) add/sample/update; PER beta annealed 0.4 → 1.0 over `TOTAL_TRAIN_STEPS`), and the DDQN learning step (online net picks the action, target net evaluates it, soft target update with `TARGET_TAU` every learn step). Learning starts only after `WARMUP_TRANSITIONS` (5k) transitions are stored. `DDQNAgent.__init__` picks a device via `get_device()` (CUDA > MPS > CPU, in that order) and moves both networks to it; all tensors built in `choose_action`/`learn` are created on that device. `Game` calls `choose_action`, `store_experience`, and `learn` each step; `Game` also reaches into agent internals directly for logging/saving (`agent.online_net`, `agent.memory`, `agent.step_count`, `agent.epsilon`, `agent.device`) and uses `agent.predict_batch(net, states)` for the periodic Q-value divergence check rather than calling the network module directly.

**Game state/physics live under `game/`:**
- `game_car.py` (`Car`) — physics (drift/traction/acceleration), 12-ray raycasting for wall sensing, hitbox-edge wall collision via line-segment intersection, and forward checkpoint-crossing detection of the front point. `Car.get_state()` returns the car's portion of the RL state vector (normalized ray distances + velocity + traction + drift angle).
- `game_track.py` (`Track`) — thin wrapper that loads a track definition from `game/track_templates/` and renders it.
- `game_grid.py` (`SpatialGrid`) — spatial partitioning so collision checks only test nearby walls, not the whole wall list. `add_wall` registers a wall in every cell holding a point of it (half-open cells, the same floor mapping queries use, so a wall on a cell border is filed only on the side whose min edge it lies on, #23), so `get_walls_in_rect` over a query's bounding box is exact to the cell with no padding; `Car.cast_rays` and `Car.check_collisions` query it through `get_walls_around(points)`.
- `game_checkpoint.py`, `game_wall.py`, `game_point.py`, `game_intersection.py` — small geometry/data classes used by the above.
- `game/track_templates/template*.py` — track layouts (walls, checkpoints, starting position/rotation); `TRACK_TEMPLATE` picks one, default `template5`. Add new tracks here. Checkpoint 0 is the start/finish line. The spawn must sit between the last checkpoint and checkpoint 0, facing checkpoint 0, with the hitbox at least `SPAWN_MARGIN` (10 px) from every checkpoint and clear of walls (#8). A checkpoint pass is a forward crossing, not an overlap (#19): `Car.check_checkpoint_crossing` asks `Checkpoint.crossed_forward` whether the car's front point moved, during the last `update()` (`car.prev_front` → `car.front`), from the previous checkpoint's side of the active line to the other, so brushing a checkpoint or crossing it the wrong way never counts; a track needs at least 3 checkpoints, each with its previous and next checkpoints on opposite sides. `Game._run_episode` counts every pass a single move makes (`Car.count_checkpoint_passes` → `game_checkpoint.count_passes`), since close or end-sharing checkpoints can be crossed in one step. `Track` calls `Checkpoint.extend_to_walls` so the crossing segment (`cross_x1..cross_y2`, used only by `crossed_forward`) runs to the walls wherever an end stops short inside the corridor. The rules live in `game/game_spawn.py` (`spawn_problems`), shared by `Game._check_spawn()` (raises at startup) and `python -m scripts.check_spawns`; run the script after adding or editing a track.

**RL state vector** = `Car.get_state()` (rays + velocity + traction + drift angle) + `[current_checkpoint_index / num_checkpoints]` + `[min(steps_since_checkpoint / STALL_LIMIT, 1.0)]`, assembled in `Game._get_state()`. If you change the ray count or append/remove features in either `Car.get_state()` or `Game._get_state()`, the two must stay in sync since `DDQNAgent`'s input layer size is derived from `len(car.get_state()) + 2` at construction time in `Game.__init__`.

**Action space** is 9 discrete actions (0=noop, 1/2=accel/reverse, 3/4=turn left/right, 5-8=combined accel+turn), mapped in `Game._apply_action`.

**Reward shaping** is progress-led (see `docs/adr/0001-progress-led-reward.md`). `Game._run_episode` adds progress from `Game._update_progress` (distance closed toward the checkpoint / `max_vel`, clipped to ±1; on a pass step the remaining distance counts as closed and the baseline moves to the new checkpoint, #14), `CHECKPOINT_BONUS` on a pass, and the crash penalty on collision/stall. `Game._compute_reward` adds small shaping terms: `SPEED_WEIGHT * speed toward checkpoint + ALIGNMENT_WEIGHT * alignment`, minus `TIME_COST` (derived as `ALIGNMENT_WEIGHT * 0.5`), plus the wall-proximity penalty. Shaping is tuned to net ~0 for aimless driving, so only progress pays. Changes to one term should be considered against the others since they're summed into a single scalar per step. `Game._angle_to_checkpoint` returns radians; the car's heading in screen space is `car.angle + π/2`.

**Persistence**: every `SAVE_EVERY` (10) episodes, `Game.save_model()` bundles everything needed to resume — online/target `state_dict`s, epsilon, step count, replay buffer arrays + priorities (via `DDQNAgent.export_state()`; `import_state()` also converts the older list-of-tuples `memory`/`priorities` format), plus episode count and top/recent reward history — into one dict and writes it with `torch.save` to `models/checkpoint_latest.pt` (always overwritten, read back on startup by `load_model()`/`DDQNAgent.import_state()`, `map_location=agent.device` so a checkpoint saved on one device loads on another). The same dict minus the replay buffer (`export_state(include_buffer=False)`, to keep the 100k buffer out of every history file) is also written to `models/history/checkpoint_ep{N:06d}.pt`; restoring one refills the buffer through a fresh warm-up, which is always fully random (`choose_action` ignores epsilon while `is_warming_up()`); `Game._prune_history()` deletes all but the newest `KEEP_HISTORY_COUNT` (5) history files, so there's always a rollback point if a run degrades. The best greedy evaluation so far is saved separately to `models/best.pt` (`Game._save_best`: the same dict as a history file plus `track`, `num_checkpoints` and the `eval` result as a dict, so copying it over `checkpoint_latest.pt` resumes from it); it is never pruned or overwritten by `checkpoint_latest.pt`, and on startup `Game._load_best_eval()` reads its `eval` back (ignored if `track` or `num_checkpoints` differs from the current track, or the `eval` dict no longer fits `EvalResult`) so a restarted run only replaces it with a strictly better round. These files are checked into the repo working tree and are expected to change on every training run — that's normal, not a sign of an unrelated diff. `models.bak/` is a manual backup snapshot, not code the agent touches.

**Logging**: `utils/csv_logger.py` (`CsvLogger`) is a small shared helper — writes a CSV header once per file, keeps the file open, and flushes every `flush_every` rows (the per-step training log uses 1000), on `flush()` (called from `save_model`) and on `close()`. `Game` owns `self.episode_log` (`logs/episode_rewards.csv`, per training episode; evaluation episodes are not in it), `self.q_value_log` (`logs/q_value_metrics.csv`, every 50 episodes from a sample of replay memory, to track online-vs-target Q divergence) and `self.eval_log` (`logs/eval_metrics.csv`, one row per evaluation round: episode, learning step, mean reward, mean/min checkpoints, mean/min laps, `new_best`); `DDQNAgent` owns `self.training_log` (`logs/training_metrics.csv`, per learning step). Add a new metric by instantiating another `CsvLogger` rather than hand-rolling `open(...).write`.
